1. 审查目标与原则 Goals & Principles

代码审查不是找茬，而是导师式的质量共建。 我们通过审查同时达成两个目标：提升代码质量，提升团队成员的工程能力。每次评论都应让作者学到东西，而不仅仅是被告知改什么。

✅ 我们追求的 / We Pursue

  • 正确性：逻辑是否真的实现了需求？
  • 安全性：有无注入、越权、敏感信息泄露？
  • 可维护性：6 个月后还能看懂吗？
  • 性能：是否有 N+1 查询、不必要的分配？
  • 可测试性：关键路径是否被测试覆盖？
  • 架构一致性：是否守住六边形架构的边界？

🚫 我们不纠结的 / We Skip

  • Tab vs Space（交给 gofmt / goimports）
  • 纯个人风格偏好（除非影响可读性）
  • 能被 linter 自动修复的问题（交给 golangci-lint）
  • 未实现功能的「更好写法」理论讨论
  • 命名审美之争（遵循命名规范即可）
🌟 核心原则 / Core Principles
  1. 具体而非笼统 — "第 42 行存在 SQL 注入风险"，而非"有安全问题"。
  2. 解释原因 — 不只说改什么，说清楚为什么这样改。
  3. 建议而非命令 — "建议用 X，因为 Y"，而非"改成 X"。
  4. 分级优先 — 每条评论标注 🔴/🟡/💭 优先级。
  5. 表扬好代码 — 看到巧妙解法或清晰模式，要点赞。
  6. 一次审完 — 不要把评论挤牙膏式分多轮给出。

3. 审查流程 Review Process

3.1 PR 生命周期 / PR Lifecycle

① 自审 Self-Review→ ② CI 自动化 CI Automation→ ③ 人工评审 Human Review→ ④ 修订 Revise→ ⑤ 批准 Approve→ ⑥ 合并 Merge

① 自审阶段（作者） / Self-Review

  • 在请求评审前，作者须先以审查者视角通读自己的 diff。
  • 运行 make all（lint + test + build）确保本地通过。
  • 检查 PR 是否只包含相关变更，无调试代码、无 fmt.Println、无 commented-out 代码。
  • 填写 PR 描述模板（见下）。

② CI 自动化阶段 / CI Automation

人工评审前，CI 流水线（.github/workflows/ci.yml）须全绿：

阶段 / Stage工具 / Tool阻断条件 / Blocker
变更检测dorny/paths-filter—（仅决定后续矩阵）
Lintgolangci-lint任何 warning 即阻断
Testgo test -race -cover测试失败或竞态检测触发即阻断
BuildCGO_ENABLED=0 go build编译失败即阻断
Docker多阶段构建仅 main 分支构建镜像

③ 人工评审阶段 / Human Review

  • 审查者应在 SLA 内（见下）完成首轮评审。
  • 按维度逐一过审：先看 安全 与 架构（阻断级），再看 Go 规范、性能、测试，最后看 部署。
  • 大 PR（>600 行）建议拆分；无法拆分时评审者可要求作者提供 walkthrough。

④ 修订与再评审 / Revise & Re-review

  • 作者针对每条评论回复「已修复 / 不同意（说明理由） / 待讨论」。
  • 不同意的评论需展开讨论，必要时拉模块负责人裁决。
  • 修订后审查者只需复审变更部分，无需全量重审。

⑤ 批准与合并 / Approve & Merge

  • 所有 🔴 Blocker 必须解决或明确豁免（豁免需记录理由）。
  • 🟡 Suggestion 建议解决，可创建 follow-up issue 跟踪。
  • 合并策略：feature → develop 用 squash；develop → main 用 merge commit（保留历史）。
  • 合并后作者负责删除 feature 分支。

4. 问题优先级分级 Priority Levels

级别标识含义处理要求示例
阻断 / Blocker 🔴 Blocker 会导致安全问题、数据损坏、架构破坏、API 契约破裂、关键路径缺错误处理 必须修复或明确豁免后方可合并 SQL 注入、未校验入参、跨层依赖、事件契约不兼容变更
建议 / Suggestion 🟡 Suggestion 不影响功能但影响质量：缺测试、命名不清、性能隐患、可抽取的重复代码 建议本次修复；确有成本可建 follow-up issue N+1 查询、缺少边界测试、魔法数字未常量化
建议 / Nit 💭 Nit 锦上添花的小改进：风格、文档、命名微调 可选；作者可决定是否采纳 注释补充、变量名更达意、文档错别字
⚠️ 优先级标注强制要求 每条审查评论必须以 🔴 / 🟡 / 💭 开头标注优先级。未标注的评论视为 💭 Nit。这样作者能快速判断哪些必须处理，避免在 Nit 上耗费过多精力而漏掉 Blocker。

5. Go 语言规范 Go Conventions

5.1 基础规范

维度要求审查要点
格式化gofmt + goimports导入分组：标准库 / 第三方 / 内部（github.com/darrell/golang-system/...）
命名驼峰；导出用 PascalCase，内部用 camelCase；首字母缩写全大写（ID、URL、HTTP）避免 data、info、temp 等无意义名
接口定义在使用方而非实现方；小接口（1-3 方法）ItemRepository 应定义在 service 包，不在 repository 包
错误错误是值；if err != nil 及早返回；用 fmt.Errorf("...: %w", err) 包装禁止吞错（_ = err）；业务错误用 apperror
context所有 I/O 函数首参为 ctx context.Context禁止用 context.Background() 替代请求 ctx（除异步任务）
注释导出函数/类型必须有 godoc 注释，以标识符开头// NewItemService constructs an itemService.

5.2 错误处理 — 本项目专项

项目已有 golang-commons/apperror 提供结构化错误。审查时确认：

  • 业务错误（NotFound/BadInput/Internal/Conflict）走 apperror，而非 errors.New。
  • 错误消息对用户友好，不泄漏内部实现（如不直接返回 SQL 错误给客户端）。
  • 用 errors.As / errors.Is 解包，而非类型断言。
❌ 不推荐
return nil, fmt.Errorf("db error: %v", err)
// 泄漏内部细节，无 HTTP 语义
✅ 推荐
return nil, apperror.Internal("create item", err)
// 带 HTTP 状态码 + 包装原始错误

5.3 并发与 goroutine

  • 启动 goroutine 须明确生命周期管理（context 或 WaitGroup）。
  • 禁止在 goroutine 中直接用请求 ctx（请求结束 ctx 即取消），需用 context.WithoutCancel(ctx) 或新建 ctx。
  • 闭包捕获循环变量需注意（Go 1.22+ 已修复循环变量语义，但仍建议显式传参）。
🔴 本项目实例：异步发布事件丢失上下文与错误 golang-app/internal/service/item_service.go 中： 
go func() {
    _ = s.publisher.PublishItemCreated(context.Background(), item)
}()
问题：① 用 context.Background() 丢失了请求的 trace/请求ID，无法串联日志；② _ = 静默吞掉发布失败，事件可能丢失而无告警。
建议：使用带 trace 的新 ctx（context.WithoutCancel(ctx)），并将发布错误记入日志或重试队列。事件丢失在事件驱动架构中是 P0 级问题。

6. 六边形架构合规 Hexagonal Architecture Compliance

本项目采用六边形架构（端口与适配器）。架构合规是 🔴 Blocker 级审查项。核心规则：依赖方向只能从外向内。

6.1 分层与依赖规则

层 / Layer位置可依赖禁止依赖
Domain 领域internal/domain/仅标准库任何外部包、service、adapter
Port 端口（接口）internal/service/service.godomainadapter 实现、HTTP/DB/NATS 具体 SDK
Service 应用internal/service/*_service.godomain + port 接口具体 adapter 实现、net/http、database/sql、NATS client
Adapter 适配器internal/adapter/port 接口 + 外部 SDK反向依赖 service 内部
Port(HTTP) 入口internal/ports/http/service 接口adapter 实现

6.2 架构审查清单

  • domain 包零外部依赖（除标准库与极少数纯类型库如 uuid）
  • service 通过接口引用 repository/publisher，不直接 import postgres / nats.go
  • 新增外部依赖（DB/消息队列/缓存）时，先在 service 包定义接口，再在 adapter 实现接口
  • HTTP handler 不直接调用 repository，必须经 service 层
  • golang-commons 不依赖任何业务服务模块（依赖方向：app → commons，不可反向）
  • 跨服务共享的类型放 golang-events（事件契约）或 golang-commons，不在服务间互相 import
  • 组合根（internal/app/app.go）是唯一允许同时知道接口与实现的地方
🔴 架构违规示例 若在 internal/service/item_service.go 中出现 import "github.com/darrell/golang-system/golang-app/internal/adapter/repository"，即为架构破坏——service 层直接耦合了 PostgreSQL 实现，使单元测试无法用 mock 替换。此类 PR 必须打回。

7. 微服务设计 Microservice Design

7.1 服务边界与数据所有权

原则本项目落实
数据库每服务独立golang-app 用 app_db（:5432），golang-app2 用 app2_db（:5433），互不直连
不共享数据库表需对方数据时走 HTTP（同步）或 NATS（异步），禁止跨服务直查 DB
服务间无强共享代码共享仅限 golang-commons（工具）与 golang-events（契约），不含业务实体
同步 vs 异步选择需立即结果走 HTTP（如建单时校验 item 存在）；解耦通知走 NATS（如 item 删除触发订单取消）

7.2 优雅关闭与韧性

  • 所有服务须实现 graceful shutdown（参考 cmd/server/main.go 模式：捕获 SIGINT/SIGTERM，30s 超时关闭）。
  • HTTP 调用须设超时（httpclient.WithTimeout），默认 30s，跨服务调用建议 10s。
  • NATS 订阅须用 queue group 实现负载均衡，避免多实例重复处理。
  • 跨服务调用失败须有降级策略（返回默认值 / 快速失败 / 重试），不能让一个服务拖垮整个链路。
🟡 超时硬编码可读性 golang-app2/internal/client/item_client.go：httpclient.WithTimeout(10*1_000_000_000) 用纳秒字面量表示 10 秒，可读性差。建议改用 httpclient.WithTimeout(10 * time.Second)，意图一目了然。

8. 安全审查 Security Review

安全问题是 🔴 Blocker，零容忍。所有 PR 须过以下安全清单。

8.1 安全审查清单

  • 输入校验：所有外部输入（HTTP 参数、事件 payload）须校验类型、长度、格式
  • SQL 注入：必须用参数化查询（db.QueryContext + $1 占位符），禁止字符串拼接 SQL
  • 路径穿越：URL 拼接用户输入须转义（url.PathEscape(id)）
  • 认证授权：受保护接口须经过 AuthContextMiddleware，校验 X-User-ID / X-Organization-ID
  • 敏感信息：密码、Token、密钥不得硬编码、不得入日志、不得入错误响应
  • 密钥管理：生产密钥走 Vault / K8s Secret，不写进 values.yaml 明文
  • 依赖安全：新增 Go 依赖须检查已知 CVE（govulncheck）
  • 日志脱敏：日志中不打印完整请求体（含个人信息）、不打印密码字段
  • 限流：公开 API 须配置限流（Istio EnvoyFilter 或中间件）
  • CORS：生产环境严格配置允许的 Origin，禁止 *
🔴 本项目实例：URL 路径未转义 golang-app2/internal/client/item_client.go 的 GetByID：c.c.Get(ctx, "/rest/v1/items/"+id, &item)。
若 id 含特殊字符（如 ../ 或空格），可能导致路径穿越或请求异常。虽 item ID 由 UUID 生成，但作为防御性编程应使用 url.PathEscape(id)。审查时应要求补充转义。

8.2 密钥与配置

场景开发环境生产环境
DB 密码docker-compose 明文（app_password）Vault / K8s Secret + Helm --set 注入

9. 性能审查 Performance Review

9.1 性能审查要点

类别检查项级别
数据库N+1 查询（循环内查 DB）；缺索引；SELECT * 滥用；缺分页🟡 / 🔴（若致生产事故）
内存大 slice 未预分配（make([]T, 0, n)）；不必要的数据拷贝🟡
并发可并发的独立 I/O 串行执行（应用 errgroup）🟡
连接池DB 连接池参数（MaxOpenConns / MaxIdleConns）合理设置🟡
缓存高频读且少变的数据未缓存；缓存未设过期/失效策略🟡
序列化热路径上反复 json.Marshal；可用 sync.Pool 复用 buffer💭

9.2 分页规范

ListItems 已对 limit 做了边界保护（>100 时回退为 20），这是好的实践。审查时确认：

  • 所有列表接口都有 limit 上限，防止恶意拉全表。
  • offset 分页在深翻页时性能差（大表考虑游标分页）。
❌ 静默修正入参
if limit <= 0 || limit > 100 {
    limit = 20
}

调用方传错值被静默改成 20，可能掩盖 bug。

✅ 显式校验返回错误（更推荐）
if limit < 0 || limit > 100 {
    return nil, 0, apperror.NewBadInput(
        "limit must be 1..100")
}

快速失败，调用方立即知道参数错了。

10. 测试审查 Testing Review

10.1 测试要求

测试类型覆盖范围强制级别
单元测试service 层业务逻辑（用 mock 替换 port）🔴 必须，覆盖率 ≥ 70%
适配器测试repository / messaging 实现🟡 建议，可用 testcontainers
集成测试HTTP handler + service + 真 DB🟡 关键路径须覆盖
契约测试NATS 事件 payload 兼容性🔴 事件结构变更时必须
竞态检测所有测试 -race 通过🔴 CI 强制

10.2 测试规范

  • 测试文件与被测文件同包，命名 _test.go（如 item_service_test.go）。
  • 测试函数命名 Test<类型>_<场景>，如 TestCreateItem_ValidationError。
  • 用 table-driven test 覆盖多场景。
  • mock 用接口实现（项目已用 NoopPublisher 等模式），避免引入重型 mock 框架。
  • 断言用标准库或轻量库（如 testify/assert），不引入 BDD 框架。
  • 每个 Bug 修复须附带回归测试。
🌟 值得推广的实践 golang-app/internal/service/item_service_test.go 已为 service 层编写带 mock 的单元测试，这是本项目的良好基线。新 service 方法提交时，须同步补充对应测试。

11. 可观测性 Observability

11.1 结构化日志

  • 统一用 golang-commons/logger（Zerolog），DEV 彩色控制台 / PROD JSON。
  • 日志须带上下文字段：request_id、user_id、entity_id 等。
  • 日志级别规范：Error 需人工介入；Warn 异常但可自愈；Info 关键业务事件；Debug 调试细节。
  • 禁止用 fmt.Println / log.Printf（绕过结构化日志）。

11.2 可观测性三件套

维度实现审查要点
MetricsPrometheus 指标（建议补充）关键业务指标（订单数、事件发布/消费数）、RED 指标（Rate/Error/Duration）
TracingIstio + Jaeger跨服务调用 trace 串联；X-Request-ID 透传（httpclient 已实现）

12. 数据库与迁移 Database & Migrations

12.1 迁移规范

  • 用 golang-migrate，文件放 db/migrations/，命名 NNNNNN_description.up.sql / .down.sql。
  • 每个迁移必须有对应的 down 迁移（除极少数不可逆操作，须注释说明）。
  • 大表 DDL 须考虑在线执行：避免 ALTER TABLE 锁表，必要时分步迁移（加列 → 回填 → 切换 → 删旧列）。
  • 迁移与代码变更同 PR 提交，确保代码与 schema 同步。
  • 破坏性迁移（删列、改类型）须分两次发布：先发兼容代码，再发迁移。

12.2 SQL 审查

  • 所有查询用参数化（$1、$2），禁止 fmt.Sprintf 拼 SQL
  • WHERE 条件字段须有索引（尤其外键、状态字段）
  • UPDATE / DELETE 必须带 WHERE，禁止全表操作
  • 事务边界合理：跨多表写操作须在事务内
  • 查询字段明确列出，避免 SELECT *（schema 变更易致问题）
  • 时间字段统一 UTC（time.Now().UTC()，项目已遵循）

13. 事件驱动消息 Event-Driven Messaging

事件契约是跨服务的公共 API，变更须像改 HTTP API 一样谨慎。

13.1 事件契约规范

规则说明级别
事件定义集中管理所有事件结构在 golang-events/events.go 定义🔴
向后兼容新增字段可选；删字段/改类型需版本化（item.created.v2）🔴
Subject 命名<entity>.<action>，如 item.created、order.canceled🟡
事件须带 ID + 时间戳用 Event[T] 信封，保证幂等与排序🔴
消费者须幂等NATS 可能重投，handler 须能重复处理同一事件🔴
Queue Group 必配多实例时用 queue group 避免重复消费🔴

13.2 发布与消费审查

  • 发布可靠性：事务内写 DB、事务后发事件（transactional outbox 模式）；或至少保证发布失败可观测、可重试。
  • 消费错误处理：handler 失败须有重试 + 死信队列，不能静默丢弃。
  • 消费顺序：若业务依赖顺序，须用 JetStream 消费者分区，不能依赖 Pub/Sub 默认顺序。
🔴 事件契约变更审查流程 任何对 golang-events/events.go 的修改须经「架构守门人」评审，且：
  1. 评估对所有订阅方的影响（搜索全部 Subscribe 调用点）
  2. 不兼容变更须协调所有消费方同步升级，或采用版本化 subject 过渡
  3. 更新 OpenAPI / 事件文档

14. API 设计 API Design

14.1 REST API 规范

规则本项目示例
路径版本化/rest/v1/items — 路径含版本号

  • 新增端点须有请求/响应 schema、错误响应、示例。
  • 建议在 CI 中加入 spectral 校验 OpenAPI 规范。

15. 部署配置审查 Deployment: Helm / Istio / Docker

15.1 Dockerfile

  • 多阶段构建：builder 阶段编译，runtime 阶段用最小镜像（alpine / scratch / distroless）
  • CGO_ENABLED=0 静态编译（项目 Makefile 已遵循）
  • 非 root 用户运行（USER appuser）
  • 基础镜像用具体版本 tag，禁止 latest
  • 合理利用层缓存：先 COPY go.mod 再 COPY 源码
  • 镜像须带 LABEL（version、maintainer、source）

15.2 Helm Chart

检查项级别
values.yaml 无硬编码密钥（用 existingSecret 引用）🔴
资源配置（requests/limits）必填🔴
livenessProbe / readinessProbe 配置正确🔴
HPA 配置（生产环境）🟡
PodDisruptionBudget 保证最少可用副本🟡
NetworkPolicy 限制跨命名空间访问🟡
values 可按环境覆盖（dev/staging/prod）🟡
helm template 渲染无报错（make helm-template）🔴

15.3 Istio 服务网格

  • Gateway 的 host 与实际域名一致，TLS 证书 credentialName 正确
  • VirtualService 路由规则与后端 Service 匹配
  • DestinationRule 熔断阈值（连接数、并发请求数、异常实例驱逐）合理
  • EnvoyFilter 限流配置不误伤内部健康检查
  • 生产环境启用 mTLS（ISTIO_MUTUAL）
  • Istio 配置变更须在 staging 验证后再上 prod
🟡 Istio 配置评审要点 istio-config/gateway.yaml 中 TLS 用 SIMPLE 模式，生产建议升级为 MUTUAL（mTLS）保护东西向流量。熔断（destination-rule-circuit-breaking.yaml）的阈值需结合压测数据设定，不能拍脑袋填数字。

16. 合并前审查清单 Pre-Merge Checklist

审查者完成评审后，对照本清单确认全部通过方可 Approve：

🔴 必须通过 / Must Pass

  • CI 全绿（lint + test + build）
  • 无安全漏洞（注入、越权、敏感信息泄露）

  • SQL 全部参数化，无注入风险
  • 错误处理完整，无静默吞错
  • 无硬编码密钥/密码
  • DB 迁移有 up + down
  • graceful shutdown 逻辑未破坏

🟡 强烈建议 / Strongly Recommended

  • 覆盖率不下降（与基线对比）
  • 新增依赖经评估且无已知 CVE
  • OpenAPI 文档已同步
  • 关键日志带 request_id 等上下文
  • 跨服务调用设了合理超时
  • 新接口配了限流
  • Helm values 资源配额已设
  • readiness 包含新依赖的健康检查
  • PR 描述完整，关联 issue

17.1 评论模板

🔴 [类型] 简短标题
第 N 行：具体指出问题位置与内容。

Why：解释为什么这是问题，会带来什么后果。

Suggestion：

        return nil, apperror.NewBadInput("name is required")
    }
    ...

17.2 礼仪规范

✅ 应该 / Do

  • 对事不对人，用「这段代码」而非「你」
  • 不确定时提问而非断言：「这里是否考虑了 X 情况？」
  • 表扬好代码：「这个 table-driven test 写得很清晰 👍」
  • 给出可执行的建议，不只指出问题
  • 大段建议用代码示例说明
  • 及时响应，尊重作者时间

🚫 不应该 / Don't

  • 用「明显」「显然」等居高临下措辞
  • 堆砌多条评论却不分级，让作者抓不到重点
  • 纠结个人偏好（命名审美、注释多寡）
  • 在已解决的评论下反复追加
  • 把架构讨论塞进单个 PR 评论（应单开 RFC）
  • 沉默数天不响应

无优先级、无定位、无原因、无可执行建议。

20. 度量与持续改进 Metrics & Continuous Improvement

20.1 审查质量度量

指标目标说明
PR 首轮响应时间≤ 4h（工作日）衡量团队响应力
PR 平均评审轮次≤ 2 轮过多说明自审不足或标准不清
CI 阻断率↓ 持续下降能在 CI 发现的别留到人审
线上问题逃逸率↓ 持续下降审查漏掉的问题数 / 总问题数
测试覆盖率≥ 70% 且不下降service 层核心逻辑

20.2 标准本身的演进

  • 本标准是活文档，每季度 review 一次，根据线上事故、新技术引入更新。
  • 每次线上事故须补充对应的审查条款（「补漏」），避免同类问题再现。
  • 新增工具/框架（如引入 Redis 缓存）时，同步增加该维度的审查清单。
  • 鼓励团队在 retro 中反馈标准是否过严或过松，动态调整。
🎯 一句话总结 好的代码审查标准 = 明确的优先级 + 可执行的清单 + 贴合项目的真实案例 + 持续演进的文化。愿本标准让 golang-system 在迭代中越走越稳。
