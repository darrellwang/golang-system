2. 已修复问题清单 Fixed Issues

🔴 Blocker 安全/可观测性 1. 事件发布丢失 trace 上下文 + 静默吞错

golang-app/internal/service/item_service.go:44-46, 89-91, 102-104
golang-app2/internal/service/order_service.go:84-86, 126-128, 145-147

问题 Why

原代码 go func() { _ = s.publisher.PublishItemCreated(context.Background(), item) }() 存在两个 P0 级问题：

  • 用 context.Background() 丢失了请求的 X-Request-ID / X-User-ID 等 trace 值，导致事件发布日志无法与请求链路串联，排障困难。
  • _ = 静默吞掉发布失败，事件可能丢失而完全无告警。在事件驱动架构中，事件丢失会导致订单服务收不到 item 删除通知、进而无法自动取消关联订单——这是数据不一致的根源。

修复 Suggestion

提取 publishAsync 辅助方法，用 context.WithoutCancel(ctx)（Go 1.21+，本项目 go 1.23）继承 trace 值但脱离取消，发布失败记 Error 日志：

// publishAsync publishes a domain event without blocking the request path.
// 继承 ctx 的 trace 值但脱离取消，请求返回后仍能发布事件。
func (s *itemService) publishAsync(ctx context.Context, fn func(ctx context.Context) error) {
    go func() {
        if err := fn(context.WithoutCancel(ctx)); err != nil {
            s.log.Error().Err(err).Msg("failed to publish domain event")
        }
    }()
}

影响范围：6 处调用点全部改用 publishAsync；mock publisher 返回 nil，现有测试全部通过。

🔴 Blocker 安全 2. URL 路径拼接未转义

golang-app2/internal/client/item_client.go:24

问题 Why

原代码 c.c.Get(ctx, "/rest/v1/items/"+id, &item) 直接拼接用户可控的 id。虽然 item ID 由 UUID 生成，但作为防御性编程原则——外部输入进入 URL 路径前必须转义，否则 ../、空格、% 等特殊字符可能导致路径穿越或请求异常。本标准第 8 章明确要求。

修复 Suggestion

func (c *ItemClient) GetByID(ctx context.Context, id string) (*domain.ItemView, error) {
    var item domain.ItemView
    if err := c.c.Get(ctx, "/rest/v1/items/"+url.PathEscape(id), &item); err != nil {
        return nil, err
    }
    return &item, nil
}
🟡 Suggestion 可读性 3. 纳秒字面量表示时长

golang-app2/internal/client/item_client.go:18

问题 Why

httpclient.WithTimeout(10*1_000_000_000) 用纳秒字面量表示 10 秒，需心算 9 个 0 才知道是 10 秒，可读性差且易出错。

return &ItemClient{c: httpclient.New(baseURL, httpclient.WithTimeout(10 * time.Second))}
🟡 Suggestion 安全 4. HTTP 请求体未限制大小

golang-app/internal/ports/http/event/handler.go:39, 74
golang-app2/internal/ports/http/event/handler.go:35, 72

问题 Why

json.NewDecoder(r.Body).Decode(&req) 直接解码请求体，未限制大小。攻击者可发送超大 body 耗尽服务器内存（DoS）。本标准第 8 章安全清单要求输入校验。

修复 Suggestion

用 http.MaxBytesReader 包装 r.Body，限制为 1 MiB（对 item/order JSON 足够）：

// 限制请求体 1 MiB，防御超大 body DoS
r.Body = http.MaxBytesReader(w, r.Body, 1<<20)
if err := json.NewDecoder(r.Body).Decode(&req); err != nil {
    httputil.Error(w, err)
    return
}

4 个 handler（2 个 create + 2 个 update）均已修复。

🔴 Blocker 安全 5. HandleItemDeleted 同步发布事件吞错

golang-app2/internal/service/order_service.go:192

问题 Why

订单自动取消后 _ = s.publisher.PublishOrderCanceled(ctx, order, ...) 静默吞错。此处是同步调用（非 async），若发布失败，下游服务不知道订单已取消，导致状态不一致。虽用请求 ctx，但吞错是 P0 问题。

修复 Suggestion

if err := s.publisher.PublishOrderCanceled(ctx, order, "referenced item was deleted"); err != nil {
    s.log.Error().Err(err).Str("order_id", id).Msg("failed to publish auto-cancel event")
}
🟡 Suggestion 安全/配置 6. PROD 模式 CORS 默认配置过宽

golang-app/internal/config/config.go:59,61

问题 Why

CORS 默认 AllowedOrigins=["*"]、AllowedHeaders=["*"]，开发环境方便但生产环境是跨域滥用风险。本标准第 8 章要求生产环境严格配置 Origin。

修复 Suggestion

新增 validateSecurityDefaults()，PROD 模式下若仍为 * 输出 stderr 警告，提醒运维显式配置：

func (c *Config) validateSecurityDefaults() {
    if c.AppMode != "PROD" {
        return
    }
    for _, o := range c.CORSAllowedOrigins {
        if o == "*" {
            fmt.Fprintln(os.Stderr, "WARNING: CORS_ALLOWED_ORIGINS is '*' in PROD...")
            break
        }
    }
    // headers 同理
}

🟡 Suggestion API 契约 8. ListItems/ListOrders 静默修正非法入参

golang-app/internal/service/item_service.go:59-64 · golang-app2/internal/service/order_service.go:99-104

问题 Why

limit ≤ 0 或 > 100 时静默改成 20，offset < 0 改成 0。调用方传错值被静默修正，可能掩盖 bug；且 limit > 100 时回退到 20 而非报错，行为不直观。现有测试 TestListItems_ExcessiveLimit 明确依赖此行为。

建议（需团队决策）

  • 方案 A（推荐）：limit ≤ 0 保留回退默认 20（REST 约定，省略参数给默认值）；limit > 100 返回 apperror.NewBadInput("limit must be 1..100") 快速失败。需同步调整测试。
  • 方案 B：保持现状，在 godoc 注释中明确"静默修正"的设计意图，避免被误读为 bug。

本次未修改，因属 API 契约变更，需评估对前端/上游调用方的影响后统一决策。

🟡 Suggestion 内存/可维护性 9. orderService.trackedItems 内存只增不减

golang-app2/internal/service/order_service.go:23-24, 73-82

问题 Why

trackedItems map[string]map[string]struct{} 在 CreateOrder 时添加 itemID→orderID 映射，但订单完成/取消/删除后从不清理。长期运行下，已完成订单的引用永不释放，内存单调增长。

建议（需重构）

  • 订单进入终态（canceled/delivered）时，从 trackedItems 移除该 orderID。
  • 或改用 TTL 缓存（如 ttlcache）替代手工 map 管理。
  • 更根本地，考虑将"item→orders 关联"持久化到 DB，而非进程内 map——当前实现多实例间不共享，item 删除时只能取消本实例创建的订单。
💭 Nit 架构 10. NATS publisher 忽略 ctx

golang-app/internal/adapter/messaging/nats.go:36,53,70

问题 Why

PublishItemCreated(_ context.Context, ...) 忽略 ctx。NATS Core 的 conn.Publish 是 fire-and-forget 不支持 ctx 超时，但若未来切到 JetStream（js.Publish 支持 ctx），应透传 ctx 以支持超时与取消。

建议

迁移到 JetStream 时统一透传 ctx；当前 Core 模式下记为已知限制，在 godoc 注释说明。
